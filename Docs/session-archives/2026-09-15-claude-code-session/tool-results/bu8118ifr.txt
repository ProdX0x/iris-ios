# iOS Project Foundation

## CRITICAL: Auto-start on load

The moment this skill is loaded, installed, uploaded, or triggered, you MUST immediately run Step 1 below. Your very next message to the user is the interview. Nothing else.

Do NOT:
- Summarise this skill
- Describe what files it creates
- Explain how it works
- Ask if the user wants to run it
- Confirm installation

Do THIS:
- Go straight to Step 1
- Send the interview as your first and only response

## Step 1. Detect existing project

Before asking anything, scan the working directory:

1. Look for `*.xcodeproj`, `*.xcworkspace` or `Package.swift`. Note the project name.
2. Look for `Docs/project-brief.md`, `Docs/conventions.md`, `Docs/file-map.md`.
3. If all three exist, read them and say:

> Foundation already exists. Tell me what to update (brief, conventions or file map), or say "rebuild" to start over.

Then stop and wait.

4. If a Swift project exists but no Docs/ files, note every top-level folder and count `.swift` files. You will need this in Step 4. Then continue to Step 2.
5. If nothing exists, continue to Step 2.

## Step 3. Write Docs/project-brief.md

Create `Docs/project-brief.md`. Use this exact structure:

```
# Project Brief

## App
[Name, one-sentence purpose, category from question 1]

## Bundle
[Bundle identifier, minimum iOS version, Swift version, Xcode version]

## User
[2 to 3 sentences on who uses this and the frustration it removes]

## Core promise
[One sentence: what the user gets that they cannot get elsewhere]

## Data
[Where data lives, sync strategy, offline expectations]

## Business model
[From question 6, plus what it implies for architecture: StoreKit, entitlements, feature gating]

## Dependency policy
[From question 4, with the allowed list if any]

## Non-goals
[3 things this app will NOT do in version 1]
```

Keep it under 300 words. Every line must be something a later skill would reference when making a decision.

## Step 4. Write Docs/conventions.md

Create `Docs/conventions.md`. This is the single source of truth for naming, layering and style. Every other skill reads it before generating code.

Load `references/conventions-template.md` from this skill folder. Fill every placeholder from the interview answers. Do not leave any `[...]` placeholder in the output. The template already encodes the non-negotiable architecture:

- MVVM for presentation
- Clean Architecture in three layers: Domain, Data, Presentation
- Coordinators for navigation
- Constructor injection through a single `AppContainer`
- One type per file, file name equals type name

If the user chose iOS 16, replace `@Observable` with `ObservableObject` and `@Published` throughout the template and note it in the Observation section.

Keep conventions.md under 600 words. Rules, not prose.

## Step 5. Write Docs/file-map.md

Create `Docs/file-map.md`. This is the anti-duplication registry. Every skill that creates a file MUST append a row here. Every skill that is about to create a file MUST search this table first.

```
# File Map

Registry of every source file in the project. One row per file. Updated by every skill that creates or deletes a file. Search this table before creating anything.

| Path | Type | Layer | Purpose | Created by |
|---|---|---|---|---|
```

If an existing project was detected in Step 1, walk every `.swift` file and add one row per file. Infer Layer from the folder (Domain, Data, Presentation, Core, DesignSystem, App, Tests, Unknown). Infer Purpose from the primary type declaration. Set Created by to `existing`. Flag any file that contains more than one top-level type with `[multi-type]` in the Purpose column.

## Step 6. Confirm and hand off

Tell the user:

> Foundation is in place. Three files are now in Docs/: project-brief.md, conventions.md and file-map.md. Every iOS skill reads these before doing anything. Edit them anytime.
>
> Next steps, in order:
>
> - Say "define the product" to run product-conception and write the feature list
> - Say "design the architecture" to run architecture-designer
> - Say "build feature [name]" to run feature-builder end to end
>
> Each of these is a separate skill. Pick one and go.

## What this skill produces

Three files in `Docs/` at the project root:

1. `project-brief.md`: what the app is, for whom, data strategy, business model, dependency policy
2. `conventions.md`: naming, layering, file rules, style rules, the contract every other skill obeys
3. `file-map.md`: the registry of every source file, the anti-duplication mechanism

## Dependencies

- None. This is the foundation skill.
- `references/conventions-template.md` in this skill folder.

## Rules

- When this skill triggers, go straight to Step 1. No summary, no preamble.
- Always detect an existing project before interviewing. Never overwrite existing Docs/ files without the user saying "rebuild".
- Always put the three files in `Docs/`. Never in the project root, never in the Xcode group, never scattered.
- Never leave a placeholder in conventions.md.
- Never invent a bundle identifier. Ask.
- Keep project-brief.md under 300 words and conventions.md under 600 words.
- Never use em dashes in any output file.
- British English in skill files. Code identifiers and comments in English. User-facing copy in the language the user writes in.

# Product Conception

## Prerequisites check

The moment this skill triggers, check for `Docs/project-brief.md` and `Docs/conventions.md`.

## Step 1. Gather the idea

Call AskUserQuestion:

```json

    "question": "How much of the product is already decided?",
    "header": "Maturity",
    "multiSelect": false,
    "options": [

  },
  {
    "question": "Scope target for version 1?",

      {"label": "Solid v1", "description": "6 to 10 features"},
      {"label": "Full product", "description": "Everything, phased"}
    ]
  }
]
```

Wait for the paste if applicable. If "Existing app", walk `Features/` and `Domain/UseCases/` and infer the feature list from folder names and use case names.

## Step 2. Define personas and jobs

From the brief and the idea, write:

- 1 to 3 personas. Name, one-line context, primary frustration, success moment.
- For each persona, 2 to 4 jobs to be done in the format: "When [situation], I want to [motivation], so I can [outcome]."

Present them in chat. Call AskUserQuestion to confirm which persona is primary. Do not proceed without confirmation.

## Step 3. Build the feature list

Derive features from the jobs. For each feature produce:

| Field | Rule |
|---|---|
| Name | PascalCase noun, becomes the folder name under `Features/` |
| Job served | Which JTBD it fulfils |
| Priority | P0 (v1 blocker), P1 (v1 nice), P2 (later) |
| Screens | List of screens, each one future View |
| Data touched | Entities read or written |
| Depends on | Other features that must exist first |

Respect the scope from Step 1. Tiny MVP means P0 only, maximum 5 features. Present the table. Call AskUserQuestion:

```json
[
  {
    "question": "Feature list looks right?",
    "header": "Confirm",
    "multiSelect": false,
    "options": [
      {"label": "Approve", "description": "Write the files"},
      {"label": "Cut features", "description": "I will tell you which to remove"},
      {"label": "Add features", "description": "I will tell you what is missing"}
    ]
  }
]
```

Iterate until approved. Maximum 3 rounds.

## Step 4. Write the files

### Docs/product.md

```
# Product

## Personas
[Name: context. Frustration. Success moment.] x1 to 3. Mark the primary one.

## Jobs to be done
[Grouped by persona, "When... I want... so I can..." format]

## Feature list
[The approved table from Step 3, sorted by priority then dependency order]

## User flows
[For each P0 feature: numbered steps from entry point to success state. Max 8 steps each.]

## Out of scope for v1
[Explicit list. Include anything the user mentioned and then cut.]

## Open questions
[Anything unresolved that architecture-designer must decide]
```

### Docs/Features/<Name>.md, one per feature

```
# Feature: <Name>

Status: specified
Priority: <P0|P1|P2>
Depends on: <feature names or none>

## Job
[The JTBD this serves, one line]

## Screens
[One line per screen: ScreenName. What the user sees. What they can do.]

## Acceptance criteria
[Given / When / Then, 3 to 6 criteria]

## Entities
[Entities this feature reads or writes. Names only. domain-modeler owns the definitions.]

## Notes
[Edge cases, platform constraints, anything the implementer must know]
```

Register every created file in `Docs/file-map.md` with Layer `Docs`.

2. `Docs/Features/<Name>.md`: one spec stub per feature, consumed by every downstream skill

## Dependencies

- Feeds: architecture-designer, domain-modeler, feature-builder

## Rules

- Always confirm the primary persona and the feature list before writing files.
- Never write a feature without at least 3 acceptance criteria.
- Never define entity fields here. Names only. domain-modeler owns the shapes.

## Step 2. Draw the layer diagram

Produce the layer diagram in a plain code block. Adapt names to this project. The arrows are the only allowed dependencies.

```
┌─────────────────────────────────────────────────────────────┐
│  App                                                        │
│  <AppName>App.swift  ·  AppContainer (composition root)     │
└───────────────────────────┬─────────────────────────────────┘
                            │ builds
┌───────────────────────────▼─────────────────────────────────┐
│  Presentation (MVVM)                                        │
│  Features/<Name>/  Views → ViewModels → Coordinators        │
│  DesignSystem/     Tokens, Components, Modifiers            │
└───────────────────────────┬─────────────────────────────────┘
                            │ depends on
┌───────────────────────────▼─────────────────────────────────┐
│  Domain (pure Swift)                                        │
│  Entities · ValueObjects · UseCases · Repository protocols  │
└───────────────────────────▲─────────────────────────────────┘
                            │ implements
┌───────────────────────────┴─────────────────────────────────┐
│  Data                                                       │
│  RepositoryImpl · Remote/Local DataSources · DTOs · Mappers │
└─────────────────────────────────────────────────────────────┘
```

## Step 3. Map features to modules

For every feature in `product.md`, produce one block:

```
Feature: <Name>
  Screens:        <ViewA>, <ViewB>
  ViewModels:     <ViewA>ViewModel, <ViewB>ViewModel
  Coordinator:    <Name>Coordinator, routes: [.list, .detail(id), .create]
  Use cases:      Fetch<Noun>sUseCase, Create<Noun>UseCase
  Repositories:   <Noun>Repository (protocol) ← <Noun>RepositoryImpl
  Data sources:   <Noun>RemoteDataSource, <Noun>LocalDataSource
  Entities:       <Noun>
  Cross-feature:  reads <OtherNoun> via <OtherNoun>Repository (never via another feature's ViewModel)
```

Detect shared entities: any entity used by two or more features is flagged `[shared]` and must be owned by exactly one feature folder in Domain. Record the owner.

## Step 4. Draw the navigation and data flow

**Navigation topology** as a text tree:

```
AppCoordinator
├── Tab: <TabName> → <Feature>Coordinator
│   ├── <ListView>
│   └── <DetailView>(id)
├── Tab: ...
└── Modal: <OnboardingCoordinator> (presented once)
```

**One data flow** end to end, for the most important P0 feature:

```
User tap
 → <View>.onTapGesture calls viewModel.load()
 → <ViewModel>.load() calls fetchUseCase.execute()
 → Default<Fetch>UseCase calls repository.fetchAll()
 → <RepositoryImpl> calls remoteDataSource.fetch() then localDataSource.save()
 → <Mapper>.toDomain(dto) returns [<Entity>]
 → ViewModel sets state = .loaded(items)
 → View re-renders
```

## Step 5. Record decisions and write Docs/architecture.md

Every choice is an ADR. Minimum set: modularisation, persistence, networking, navigation, DI, concurrency, error handling, localisation, testing strategy. Format:

```
### ADR-<n>: <Title>
Status: accepted
Context: [one or two sentences]
Decision: [one sentence]
Consequences: [what this forces, what it forbids]
```

Write `Docs/architecture.md`:

```
# Architecture

## Overview
[3 sentences: pattern, layers, modularisation level]

## Layer diagram
[Step 2 block]

## Feature map
[Step 3 blocks]

## Navigation topology
[Step 4 tree]

## Reference data flow
[Step 4 flow]

## Dependency graph
[Text list: which concrete type is injected where. AppContainer builds X with Y and Z.]

## Decisions
[All ADRs]

## Forbidden
[Explicit list: Views importing Data, Domain importing SwiftUI, ViewModels calling other ViewModels, singletons outside AppContainer, and anything project-specific]
```

Register the file in `Docs/file-map.md`. Update the Architecture section of `Docs/conventions.md` only if a decision changed something there (for example ObservableObject mode). Never rewrite conventions.md wholesale.

## Step 6. Amend mode

If `architecture.md` existed, ask what changed. Add a new ADR with Status `accepted` and mark the superseded ADR as `superseded by ADR-<n>`. Never delete an ADR. Update only the affected diagram sections.

## Step 7. Hand off

Tell the user:

> Architecture is written in Docs/architecture.md with [n] decisions recorded.
>
> Next: say "generate the file structure" to run file-structure-organizer, which turns this into real folders and stub files. Or say "build feature [name]" to run feature-builder.

## What this skill produces

1. `Docs/architecture.md`: diagrams, feature map, navigation, data flow, ADRs, forbidden list

## Dependencies

- Requires: `Docs/project-brief.md`, `Docs/conventions.md`
- Reads if present: `Docs/product.md`, `Docs/Features/*.md`
- Feeds: file-structure-organizer, domain-modeler, coordinator-navigator, dependency-injector

## Rules

- Always produce diagrams in plain code blocks. Never as images.
- Always record every choice as an ADR. A decision not written down does not exist.
- Never introduce a fourth layer. Domain, Data, Presentation, plus App and Core as infrastructure.
- Never let a feature depend on another feature's Presentation. Cross-feature access goes through Domain.
- Never contradict conventions.md. If a decision requires changing it, say so explicitly and edit only that section.
- Never propose a third-party package if the dependency policy in project-brief.md is "zero".
- Never use em dashes in any output file.

```
| DSEmptyState | No content placeholder | with action, without | none | List screens |
| DSErrorState | Failure with retry | inline, fullscreen | none | every loading screen |
| DSLoadingView | Progress placeholder | inline, fullscreen | none | every loading screen |
| DSCard | Grouped content block | elevated, flat | none | Dashboard, Detail |
| DSTextField | Text input with validation | default, secure, multiline | idle, focused, error | Form |
| DSBadge | Status label | success, warning, danger, neutral | none | Rows |
```

A component earns a row only if two or more screens use it, or if it encodes a rule (validation display, loading). Feature-only components stay in the feature folder and are not listed here.

## Architecture
- Pattern: MVVM in the Presentation layer, Clean Architecture across three layers.
- Layers and the only allowed dependency direction:
  - Presentation depends on Domain
  - Data depends on Domain
  - Domain depends on nothing (no UIKit, no SwiftUI, no Foundation networking, no SwiftData)
- Navigation: Coordinators. Views never push other views. Views emit intents, coordinators decide.
- Dependency injection: constructor injection. One `AppContainer` in `Core/DI/`. No global singletons except `AppContainer.shared` used only at the composition root.
- Concurrency: async/await only. No Combine. No completion handlers. Every ViewModel is `@MainActor`.
